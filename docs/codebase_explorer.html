Engineering Reference / acidcat byte-level format dissector

acidcat: byte-level dissection and reverse-engineering of audio & sampler formats

A pure-Python scalpel for audio and preset files. It walks a container's real byte structure, names every field, recovers audio from raw blobs and console ROMs, repairs broken headers by re-satisfying their constraints, and -- wearing its second hat -- listens to the audio itself to catalogue a sample library. One engine underneath both. v0.90.0 pure Python 3.9+ core deps: mutagen only github.com/hed0rah/acidcat

Source tree

core/ is organized by concern, and the ordering below is also the dependency direction: everything above may be imported by everything below it, never the reverse. That is what lets the base install ship with only mutagen while the heavier tiers stay optional.

Data flow

Three paths matter. The dissection path is the tool's spine: magic bytes in, a named field tree out, and one place where a hostile file is allowed to degrade rather than crash. The recovery pipeline is the reason the verbs compose. The catalogue path is the second hat, and the only one that pulls heavy dependencies.

The two hats, and the seam between them

acidcat reads a file two ways. The byte hat asks what the container claims about itself -- chunk layout, declared sizes, field values, where the audio physically sits. The sound hat asks what the audio actually is -- its tempo, its key, its timbre. Most tools do one or the other. Doing both over one engine is the point: the byte layer is what finds and decodes the audio that the sound layer then listens to.

  • The seam is a strict dependency direction. Nothing in the lean core imports analysis/ or catalogue/ -- verified by a static invariant in the suite, not by convention. So pip install acidcat is a working byte-dissection tool with one dependency, and librosa arrives only when you ask for it.
  • Capability degrades rather than disappearing. With the analysis stack absent, detect still answers from filename and path parsing, which is pure regex and has no business being gated behind numpy.
  • Where both hats need the same primitive, it lives in primitives/: the same lag-1 autocorrelation that decides "is this region audio?" during forensic recovery also gates the ROM rippers.

Under the hood: the byte hat

The never-raise contract

  • A dissector points at hostile input by definition -- corrupt files, deliberate fuzz, half-downloaded samples. The rule is that a walker degrades with warnings and never raises, and it is enforced at the single boundary every consumer shares rather than in 33 walkers individually.
  • The test suite flips ACIDCAT_WALKER_RAISE=1, so the same code path that shields a user from a walker bug turns that bug into a loud traceback in CI. Degradation in the field, strictness in the lab.
  • Generic triage catches the middle case: a file with no dedicated walker but obvious chunk structure still gets its grid surfaced, so an unknown container is a partial answer instead of a rejection.

Reading a chunked container

  • RIFF/WAVE and its IFF cousins are the workhorse: a 4-byte id, a 32-bit size, payload, and a pad byte when the size is odd. Endianness flips between RIFF (little) and AIFF/FORM (big), and that single difference is why the walkers stay separate rather than sharing a clever parameterized iterator.
  • Loop and tempo metadata hides in optional chunks: smpl carries the MIDI root note and loop points, acid carries the beat count and tempo that samplers actually read. acidcat treats a root note of zero as unset rather than as C-1, because that is what writers mean by it.
  • MPEG audio has no container at all -- just a frame sync pattern -- so the walker validates a candidate header, then confirms by walking to where the next frame should begin. That resync logic is also what lets forensics find headerless MP3 inside a raw blob.
  • FLAC is a metadata block chain whose STREAMINFO is fixed at 34 bytes -- a strong enough invariant that the signature sweep uses it to reject a stray fLaC in noise.

Write is repair is re-satisfying constraints

  • A container is a set of fields, some free and some derived -- a master size is a function of everything after it, an offset is a function of where its target really sits. A derived field that disagrees with its function is a Violation.
  • That framing collapses four verbs into one idea: validate and audit report violations, repair fixes them, and write mutates first and then fixes. There is no separate "writer" that could drift from the "checker".
  • The honesty rule is the witness: a violation is repairable only when some independent source of truth exists -- end-of-file for a master size, the target's real position for an offset. No witness, no automatic fix, and the report says so rather than guessing.

Finding audio that has no header

  • Signature carving finds files by their magic. Raw PCM has no magic, so a signature scan walks straight past it. The statistical detector fills that gap using the property that makes audio compressible in the first place: consecutive samples are similar, so the lag-1 autocorrelation is high while noise sits near zero. Compressibility and detectability are the same coin.
  • locate runs both engines plus a frame-cadence scanner, then reconciles them: a statistical hit inside a container's extent is part of that file, not a separate find. A missing header never discards a hit -- it only downgrades a container recovery to a blob recovery.
  • Geometry inference asks how to read the bytes: 8- or 16-bit, mono or stereo, big- or little-endian, by picking the interpretation that comes out smoothest. Sample rate is not recoverable from the bytes, so it is reported as null with candidates rather than invented.
  • The transform lens handles audio hidden under a cheap reversible obfuscation -- XOR, bit-rotate, nibble-swap. These preserve entropy but scramble autocorrelation, which is exactly how they slip past the detector; the lens un-applies each candidate and asks whether it is audio now.
  • The same idea scales to cartridges. ROM rippers sweep an N64 or SNES image for decodable VADPCM or BRR runs and keep the ones that decode to coherent audio -- recovering samples without the bank structure that named them.

Codecs

  • The ADPCM family is one idea in many dialects: store a small delta and a per-block predictor rather than absolute samples. Sony's PS-ADPCM, the GameCube's DTK, and CD-XA all share the same 2-tap filter table, which is why it now lives once in primitives/pcm.py.
  • SNES BRR packs 16 samples into 9 bytes with a 4-bit shift and a 2-bit filter selector, and every block carries an end flag -- which is what makes a container-agnostic sweep of a ROM possible at all.
  • Kontakt NCW is lossless, not protection: a DPCM predictor, bit-truncation, and mid/side. Decoding it is the same class of work as decoding FLAC, and acidcat treats it that way.

Under the hood: the sound hat

  • Key detection correlates a 12-bin pitch-class profile against the Krumhansl-Schmuckler major and minor templates across all 24 rotations. A benchmark on real material put it around 67-72% on pitch class for tonal content, and notably weaker on mode -- so the result is reported with its source, never asserted as ground truth.
  • Metadata beats inference. A smpl root note or an acid tempo written by the tool that made the file is more trustworthy than anything derived from the waveform, so detection is layered: chunk metadata, then filename, then analysis, with the winning source recorded in the output.
  • The feature vector is 51 dimensions of timbre and dynamics, extracted at a fixed 22050 Hz so vectors from different source rates are actually comparable -- a spectral centroid computed over a different frequency range is not a comparable number.
  • Harmonic compatibility uses the Camelot wheel: neighbours on the wheel, the relative major/minor, and half-/double-time tempo matches, which is how a DJ or producer actually thinks about whether two loops sit together.

Storage

One SQLite database per library, not one global index -- a library is a folder you registered, and its index lives beside the registry entry rather than in a single monolith. Queries fan out across registered libraries and merge.

# registry + per-library databases ~/.acidcat/registry.db the libraries you have registered ~/.acidcat/libs/<label>.db one index per library # samples table, abridged path TEXT PRIMARY KEY normalized, comparable across platforms format TEXT bpm REAL key TEXT duration REAL acid_beats INT loop metadata, straight from the chunks features BLOB the 51-dim vector, versioned feature_set_version INT stale vectors are re-extracted, not compared
  • One filter builder serves both the query verb and the MCP search_samples tool, so the two surfaces cannot drift apart in what they support.
  • Vectors carry a version. When the extraction changes, old vectors are not silently compared against new ones -- candidates are filtered to the current version and a stale target is re-extracted live.

Command-line surface

The vocabulary is deliberately narrow: one word, one meaning, everywhere. That was not free -- --format previously did three unrelated jobs -- and the split follows how tools that handle both file formats and output formats disambiguate them.

wordmeansflag
formatthe file's container/codec (WAV, FLAC, MP3)--format where a verb filters or forces the input type
outputwhere bytes go; stdout by default-o / --output FILE
output-formathow records are rendered--output-format, with --json / --csv
encodinghow carved bytes are serialized--encoding raw|hex|c|py|b64
  • Verbs compose like coreutils: - means stdin on the byte-analysis verbs, structured output goes to stdout while summaries go to stderr, and exit codes follow the grep family so && chains behave.
  • Nothing switches the shape of output based on whether stdout is a terminal. Only color does, via --color auto|always|never honoring NO_COLOR. A script that redirects output gets exactly what it would have seen on screen.
